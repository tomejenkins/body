# Phase 7.6A — Technical audit and hardening plan

Audit date: 2026-11-10 UTC. Reviewed base: `932e7e8`, merged PR #26. Branch: `audit/phase-7-6a-technical-review`.

## Executive summary

The primary entry, selection, logger, schedule, Favorite and completion paths are implemented on a coherent owner-scoped session engine. The existing tests are substantial, and fresh local validation is recorded separately. This audit found **no demonstrated cross-owner disclosure, duplicate active session or irrecoverable loss** in the tested paths. That is bounded local evidence, not a hosted security certification.

Four findings deserve attention before expanding the product:

1. **P1: inconsistent qualifying evidence.** Two confirmed external-load bench sets at zero weight resolve a prescribed program position, despite contributing zero qualifying sets to the existing performance engine. A zero-repetition program session can also carry a stored `full` label while its effective program progress is zero. These are reproducible semantic inconsistencies, not hypothetical migration risks.
2. **P2: lifecycle operations need an authoritative transition contract.** Direct owner-authorized assignment archival can currently leave its attached workout active. Normal workout starts protect active sessions; the remaining raw lifecycle DML is insufficient for the locked 7.6B operations.
3. **P2: uncertain-save retry can need avoidable conflict review.** A committed response deliberately dropped by the test leaves the draft unconfirmed, correctly. An ordinary Retry click then reproducibly surfaces a stale-revision conflict in the exercised sequence. Explicitly reviewing the already-saved version recovers it without duplicate sets or a second revision. This needs a focused interaction/queue investigation, not an optimistic-success workaround.
4. **P2: build-tool supply-chain advisories.** The registry scan reports four high and seven moderate entries in build/lint dependency paths; runtime-only scanning is zero. Reachability and a compatible pinned remediation need review before release.

Logging is measurably network-sensitive locally. Each ordinary edited-set save produces two browser action requests and six upstream calls, including four Auth reads. Small-fixture database execution is much shorter than the browser round trip. This does **not** establish the cause of the user's real cellular latency or justify removing authentication. No production optimization, schema migration, UI change, logging behavior change or follow-on feature is implemented here. Delivered changes are audit documentation, local instrumentation, numeric evidence and probes.

    participant D as PostgREST/Postgres

    D-->>N: Authoritative selection set rows
    N-->>Q: Action result
    Q->>Q: Reconcile revision/sequence; Saved only on result
    Q->>N: Existing asynchronous continuity action
    N->>A: Middleware getUser
    N->>A: Action getUser
    N->>D: workout_continuity
    D-->>Q: Current authoritative timer/status

Exact call sites on the audited base:

- `src/components/sets/workout-logger.tsx:338–540`: immediate draft persistence, queue, stable retry command, sequence-aware reconciliation and retained failure state.
- `:1127`, `:1143`: dirty weight/reps blur can enqueue. Completion explicitly enqueues; its control is disabled while pending. `:1166` renders Saving/Not saved/Unsaved/Saved from current state.
- `src/features/sets/actions.ts:14–109`: input validation, verified Auth, RPC, optional conflict-only current-row read. **No per-set `revalidatePath`**; unit/effort preference actions below it do invalidate their own views.
- `src/lib/supabase/update-session.ts:14–62`: independent middleware verification. `src/features/continuity/actions.ts:5–33`: the follow-up action verifies again and reads continuity.
- `supabase/migrations/20261105183319_advanced_set_effort.sql:21–75`: effective set RPC. It locks the owned session, checks continuity/closed state, recognizes the last mutation, rejects stale revisions, updates actuals/status and returns all set rows for the selection.

Observed normal save: two browser POSTs, each with two Auth GETs and one RPC. The continuity response usually follows the Saved DOM transition; it is not a second completion acknowledgement. Framework action serialization can make follow-up work compete with subsequent actions. Conflict recovery adds a set-row SELECT; expiration/focus/visibility or explicit pause can create other calls. Those are separate scenarios, not included in the ordinary-save count.

There is no routine full-workout/catalog/history refetch or cache invalidation on an ordinary set save. Initial page/navigation loading is different: `loadWorkout` reads continuity, session, paged selections, paged sets and preferences sequentially; movement loading then reads catalog/matching and prior choices. `ProtectedLayout` also reads continuity, and `ActiveWorkoutBar` refreshes on mount/focus. These are candidates for **request-scoped** deduplication after measuring page navigation, not evidence of per-keystroke catalog reloads. Private cross-user caching is inappropriate.

- All 36 measured operations produced **two completed browser fetches**. Median total serialized request bodies were 415–416 bytes; total encoded response bodies 1,160–1,166 bytes for this three-row fixture. These exclude HTTP headers/TLS; Resource Timing transfer size is not a packet capture.
- Matched server mutation spans: p50 **35.23 ms**, p95 **52.79 ms**; three upstream calls per mutation, exactly two Auth reads. RPC transport p50 **8.94 ms**, p95 **16.33 ms** includes PostgREST/network/serialization, not just database execution. A local outlier reached 216 ms; this small sample cannot identify its cause.
- Database-only authenticated function timing: 30 calls, median **0.9745 ms**, p95 **2.9952 ms**, mean **1.3257 ms**, maximum **4.327 ms**. Separate `EXPLAIN (ANALYZE, BUFFERS)` execution: **1.018 ms**. Small warm local fixture, not production volume/concurrent-load performance.
- DOM transition after the mutation resource's complete-response endpoint: medians approximately **3.9–4.9 ms**, with no >50 ms browser long tasks observed. This is a reconciliation proxy, **not React CPU profiling or paint timing**. One -2.6 ms value reflects stream-tail/observer ordering; it is not evidence of speculative successful-save behavior.
- Playwright's polling-based confirmation was 848.95 ms median in the 300 ms profile, while the actual DOM observer recorded 355.90 ms. Polling overhead must not be reported as user-visible app rendering cost.
- Instrumented local median was 10.1 ms above the control; variability/outliers and nonrandom sequential runs prevent assigning that difference solely to instrumentation. These are baseline observations, not a measured optimization gain or an SLO.

**Interpretation:** induced browser latency increased actual confirmation time; database execution was small in this fixture. The user's real connection, edge region, Auth/database distance, cold starts, radio variability and hosted query plans were not measured. Emulation affects the browser leg, not the server-to-Supabase leg. No safe production performance gain was demonstrated; none was implemented.

## 7.6B program lifecycle feasibility and contract

Existing identity is sufficient; **do not create another enrollment table**. `program_assignments.id` already distinguishes repeat enrollments. The probe archives an assignment, reenrolls in the same version and observes two assignments, exactly one active, and three retained old sessions. A new assignment is created once the old one is terminal; starting the same version while still active currently continues it.

Current normal path: `start_program_workout` (`20261105221401_in_workout_program_selection.sql:62–90`) locks profile, validates nonce, rejects active workouts and creates the session. Effective binding in `20261106220839_adaptive_program_scheduling.sql:171–201` archives a different active assignment and inserts a new one in that transaction. This is a useful atomic foundation, but is **not** a standalone Start Program / Switch / End management API.

Confirmed lifecycle gap: an authenticated owner can update their active assignment to `archived` while its session remains `in_progress`. Grants remain in `20261103174917_enable_database_security.sql:164`; schedule input stamps an end time but does not prohibit this transition during active training. The probe prints `assignment_state=archived, workout_state=in_progress`. This does not leak another owner's data; it demonstrates why 7.6B cannot rely on raw client UPDATE or an archive-then-start UI sequence.

Recommended durable additions to existing assignments: server-owned enrollment/end timestamp provenance, terminal reason, lifecycle revision, and an optional exact-assignment pending-end request (`requested_at`, request UUID). Add a small typed owner-scoped **command receipt** contract for payload-bound retries/results across start/end/cancel/switch. Receipts are not workout completion truth or a second event-sourced scheduler. Narrow existing lifecycle grants and route authorized commands through invoker operations plus validated triggers, following existing schedule/timer command conventions. Do not introduce a privileged public RPC merely to bypass RLS.

| Locked operation       | Proposed atomic behavior                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start Program          | Validate owner, approved/readable immutable source, confirmed start date/zone, no conflicting active workout/assignment; create a fresh assignment with server time and enrollment nonce, without creating a workout. Repeat enrollment creates a new ID. Reject rather than silently replace an active program.                                                                                                                              |
| End Program Now        | Confirmation in future UI; exact assignment/revision/request; profile/assignment locks; reject any in-progress workout until explicitly resolved; set terminal reason `ended_now` and server end time. Never mark it fully completed.                                                                                                                                                                                                         |
| End After Next Workout | Persist pending request on exact active assignment; show/cancel through the same revisioned command path. At the next newly closed qualifying **fully prescribed** assigned session, an AFTER-status transaction hook resolves the request and closes that assignment atomically. Do not consume it for a Favorite/ad-hoc session, partial acceptance, skip, abandonment, empty/zero/unsupported work or a historical already-closed session. |
| Cancel pending end     | Exact assignment/revision, payload-bound retry, no fabricated completion; clear pending status while retaining the request receipt/result. Serialize cancellation against closure: whichever transaction wins determines the observed state.                                                                                                                                                                                                  |
| Switch Program         | Both Browse and active-management links lead to one confirmation and the same transition RPC. Validate replacement first; reject active workouts; atomically terminalize old assignment as `switched` and create the replacement. Retry returns those same identities. Never expose archive/start partial failure.                                                                                                                            |

Hook placement matters: effective qualifying fullness must read the committed session status and saved sets **within the closing transaction**, after existing BEFORE completion triggers have run. Do not call a completed-only source from a BEFORE trigger while the row still reads in-progress, and do not use a background/client timer. Duplicate end calls currently return without a second status write; the new hook also needs pending-request/state CAS guards. For simultaneous fixed-duration fulfillment and pending-end intent, propose actual fixed-duration completion as terminal reason, with the pending request recorded as satisfied by that same session; preserve the user's end request as intent, not a second transition.

Fixed-duration calendar completion is currently derived and does not necessarily terminalize `program_assignments.state`. Old version launch forms can still start explicit training; `start_assigned_workout` validates cursor identity but does not independently prohibit a complete cursor. 7.6B must define the terminal transition and repeat-enrollment confirmation; it must not relabel existing archived enrollments as completed.

Legacy `started_at` INSERT grants and unconfigured lifecycle state were historically owner-controlled. Normal current binding uses server defaults, but existing data is not universally certified enrollment evidence. Preserve it with an honest legacy/provenance label; do not backdate an exact new enrollment from unrelated workouts. New commands must make time server-authoritative. Travel does not change the assignment scheduling timezone.

## Program statistics and Program History proposal

### Membership, counts and duration

- Enrollment key: exact owned assignment UUID and immutable source version. Same template enrolled twice produces two cards/details. Use immutable version/program/day snapshots for original attribution, not today's editable template name.
- Associated workout history: exact `program_assignment_id`; independent/Favorite sessions remain excluded even when exercises/day names match. No attribution by coincidental timestamp or canonical exercise alone.
- Qualifying completed training count: distinct completed sessions with at least one eligible working set, separately break out effective full and partial training. A repeat is another actual workout, not another unique program occurrence. Skips/accepted partial decisions are not fully completed workouts.
- Completed rotation/progress uses distinct assignment/version/rotation/day occurrence resolution, preserving the current earliest gap and nonweekly structure. Show intentional skip/acceptance separately from actual full rotation completion.
- Statistical period: canonical server enrollment start through server end (or requested `as_of` now for active), with eligible session `finished_at` inside that closed interval. Keep exact-assignment sessions outside a legacy/corrected interval visible as associated history with an explicit exclusion reason; do not silently rewrite timestamps or force them into a different enrollment. Normal new end/switch commands prevent active-session boundary crossings.
- Preserve exact start/end instants and a stable enrollment display zone. Short duration can show whole elapsed days/weeks with exact dates available; long duration uses calendar-anniversary years/months plus remainder, clamping month ends explicitly (Jan 31 → Feb 28/29). Do not divide by 30-day months or 365-day years. Specify and test UTC-instant elapsed duration versus local calendar labels around DST; tooltip/details retain exact instants and zone. Legacy unknown end time is unavailable, not inferred from last training.
- Status vocabulary: Active; Completed only when the actual fixed-duration rule and terminal reason support it; Ended with truthful reason for early end/switch. Archived is existing storage/lifecycle state, not proof of full completion. Do not merge paused/archived legacy assignments into a synthetic continuous history.

### Comparable strength improvement

Use `performance_source` and existing metric logic with the exact assignment membership/period gate. Contract key: `(canonical exercise UUID, measurement category, metric, exact repetition key)`.

For an observed 5-rep load improvement, baseline is the **best eligible five-rep set in the first qualifying session containing that exact metric** within the enrollment. Compare it with the best eligible five-rep load in a strictly later qualifying session. Do not choose the lightest initial set, a warm-up, a pre-enrollment all-time PR, or a different rep count. Tie-break baseline sessions by finished time then session UUID and sets by established deterministic ordering. Show a positive delta only when subsequent value strictly exceeds baseline. If only one comparable session exists, show baseline/insufficient comparison; no invented “weight added.”

Actual 1/3/5-rep observations are separate comparisons; one heavy five does not establish a true triple. Estimated 1RM is a separately labeled estimate using existing supported formulas, never direct observed weight added. Compare canonical kg and round only at display; preserve actual entered-unit precision. Changing preferred units changes presentation, not baseline or membership. Bodyweight repetitions are a reps metric; added resistance is not inferred body mass; assisted/duration/unsupported data does not enter a strength delta. No unrelated exercises or movement families share a load baseline.

Derive aggregates; avoid mutable workout counts/best-lift columns. At most one or two display highlights can be selected deterministically from valid deltas without dropping the full detail data. Later archive/deletion/corrections must recompute both baseline and subsequent best, so removing the earliest session may change the baseline legitimately.

### Views and historical edge cases

7.6B adds the locked **Workouts | Programs** selector inside History, default Workouts, preserving its chronological pagination and logger behavior. Programs lists separate owned enrollments including current active, with status, exact dates/human duration, qualifying workout count and valid lift highlights. Detail loads immutable attribution, enrollment reason/dates, paged associated workout links, comparable lift metrics and optional existing rotation summary through batched owner-scoped reads.

Late completion belongs to its original assignment; out-of-order/repeated days retain original source day/rotation. A switch cannot silently transfer sessions. Archived templates retain immutable versions/snapshots. Fixed-duration completion and user early ending are separate reasons. Evidence corrections/archive/delete affect derived training counts and progress, not assignment existence or original enrollment identity. No history card may imply a skipped or ended program was fully completed.

## 7.6C archive/delete dependency map

There is **no implemented session archive/restore/delete workflow**. Current root DELETE grants are denied, closed set edits are guarded, and exercise/Favorite archival is different from workout archival.

Recommended small central eligibility mechanism: owner-scoped eligible-session relation/helper plus the existing eligible-set source. New server-owned archive/deletion markers gate active analytics, defaults and program evidence consistently. Archive retains all actuals and structure; normal History excludes it; Archived History explicitly includes it; restore clears archival status once and all consumers derive again. Owner-private archived review can display its retained workout facts while clearly distinguishing excluded current analytics. Do not silently treat archived training as a skip or produce a replacement session.

Archiving/removing completion evidence reopens the corresponding unresolved occurrence when no other eligible session resolves it. An explicit skip remains independent intent. Accepted partial resolution must stop relying on withdrawn source evidence while retaining its immutable decision record. Restoring the original eligible session can resolve its original identity again, deduplicated by occurrence, never by incrementing a mutable count. A terminal enrollment must not automatically reactivate when evidence is withdrawn, especially after switching to another active program. Retain the original end/transition receipt as historical intent, recompute effective completion from remaining evidence, and display a completion-evidence-changed state instead of continuing to claim full completion. End-after-next intent remains ended; its withdrawn training evidence does not become a qualifying workout count. Existing `decisionRevision` is a decision count: review extending the stale-write token to include evidence revisions before archive/restore affects decisions and management clients.

### Proposed permanent deletion model

Separate **application-visible permanent deletion** from physical root erasure and backup retention. Recommended staged contract:

1. Owner-authorized, explicitly confirmed, idempotent delete request locks profile/session and rejects in-progress sessions. Verify exact assignment/Favorite/scheduling references; never silently end training.
2. Mark the session non-restorable and immediately exclude it from both normal and Archived History and every training consumer. A minimal identity tombstone can retain assignment/version/day/rotation keys required by immutable decision/configuration references, without exposing a review route.
3. Transactionally remove actual set evidence and performed movement/selection data, redact free-text actual-workout payload as required, and retain only the minimum approved identity/audit receipt. Existing immutable source/closed-child guards need an explicit, narrowly scoped deletion-receipt path. A validated owner-only receipt, parent locks and exact child membership can authorize this cleanup without a spoofable GUC or a broad SECURITY DEFINER bypass. Do not simply grant unrestricted closed-history writes. Prove rollback and foreign-owner denial at every stage.
4. Keep assignment/enrollment history as its own record. Accepted-partial/source-first-session references can point at the minimal tombstone while no longer supplying eligible performance. If physical root deletion is chosen instead, forward-migrate these FK/check semantics deliberately; `ON DELETE CASCADE` of immutable decisions is not acceptable.
5. Existing Favorite structural snapshots remain reusable where their chosen canonical exercises remain accessible. They must not retain deleted actual weights/reps, notes or PR claims; copied immutable structure is not training evidence. A deleted source cannot be newly loaded to create another Favorite.
6. Revalidate all derived private views and request identities; refetch current records from eligible evidence rather than leaving a previously best value cached. Private no-store rendering helps but does not replace correct client invalidation or source eligibility.

A tombstone-only implementation that retains all actual sets is **not** the proposed final cleanup. Full physical erasure from backups/PITR is not promised; define retention, access, restoration/re-deletion procedures and privacy policy separately. None of this deletion capability or a cleanup bypass is implemented in 7.6A.
